# 眼镜式双摄融合眼动仪 v2：Pi Zero 2 W 一体化方案 + 密集文字遮蔽

> **2026-10-30更新（摄像头选型变更，见`261004/experiment_report.md`第7i节）**：本文档写于2026-10-10，当时瞳孔摄像头方案是OV9281+外挂850nm IR补光。后续实测中OV9281模块体积过大，无法按原计划直接固定到镜架前端，三棱镜反射方案也验证不可行（7i.1节）。改用GC0308模组（近距离眼动设计，物理上更小更易固定），配合EllSeg深度学习检测器（无需主动IR补光），静态图复测真实成功率86.9%、刚性固定安装后连续视频公平帧成功率100%（7i.6/7i.10节）——**这条路线已验证完整，GC0308取代OV9281成为瞳孔摄像头的最终选型**。本次更新把下文涉及摄像头选型、IR补光、检测算法依赖的部分同步修改，其余内容（场景摄像头、PCB排布、密集文字遮蔽方案）未受影响，保持原样。**有一处新增的重要风险尚未验证，见"三、3.2节"的标注：EllSeg是深度学习模型，实测在PC上也只有约6-8FPS，Pi Zero 2 W的算力远弱于PC，这个数字能不能用还是未知数，需要单独排期验证，不能假设能直接照搬。**物理层面：ESP32-CAM、OLED、GC0308三件已按261016节的装配方案固定上镜架（用户2026-10-30确认），下一步是称重+试戴（见`261004/experiment_report.md`7i.11节），本文档第一节硬件清单"镜架本体"/"供电"相关内容尚未因此更新，待称重结果出来后再定是否需要调整配平方案。

## Context

v1计划（ESP32CAM做场景识别）存在根本性算力缺陷：ESP32CAM是单/双核MCU级芯片，连轻量级目标检测模型都跑不动，且UART传图带宽上限极低（只能做1-3FPS快照，不能做连续处理）。用户指出此问题后，重新讨论确认：

1. **随身算力单元**：Raspberry Pi Zero 2 W（四核Cortex-A53），能跑完整Linux+原生OpenCV，可以直接复用本项目已验证的 `pupil_detector.py`（Haar cascade + Otsu阈值 + 轮廓检测）的算法逻辑，不需要换开发框架。已查证Luckfox Pico Max（RV1106,带1TOPS NPU）作为对比：官方论坛明确指出其原生OpenCV体验很差、不建议用于目标检测服务，需要学习RKNN/MPI专有框架，对当前阶段不合适——故排除。**（2026-10-30更新：瞳孔检测算法后来从`pupil_detector.py`换成了`pupil_detector_ellseg.py`，见下文3.1/3.2节的风险标注，这里保留原文只是为了记录当时的判断依据，不代表这个算法选择到现在还成立）**
2. **前置场景摄像头**：放弃ESP32CAM方案，改用Pi Zero 2 W自带的CSI摄像头接口直接接场景摄像头模块。这从根本上消除了UART带宽瓶颈（图像直接进Pi内部处理，不需要串行传输），而不是把瓶颈转移到别处。ESP32CAM+现有OLED组合作废/闲置。
3. **显示方案**：潜望镜式反射（OLED通过镜腿光路反射投到镜片上）。已向用户说明其物理局限——OLED是发光叠加，不能做真正的"遮光/替换"式模糊，只能做"视觉掩蔽"：用密集亮文字图案叠加在干扰物位置，利用视网膜叠加+密度足够高时难以分辨背景细节的效应，达到近似遮蔽效果。局限已向用户说明并被接受：效果随环境光减弱（户外强光下基本失效）、非确定性像素处理、物体边缘可能透出。
4. **物理集成**：Pi Zero 2 W本体和CSI场景摄像头都装在镜架本体上（而非分体放腰间），只引出一根供电线到腰间/衣服上的电池包。这避免了CSI软排线跨过镜腿到腰部可能面临的信号衰减/接触不良风险（排线超过15-20cm就不稳定），是本方案优于"算力盒分体放腰间"方案的关键原因。
5. **干扰物判定**：先用闭集预定义分类（如"手机屏幕""电视""广告牌"等固定类别），用轻量级传统视觉特征或小型量化分类器实现，不做开放式通用检测（算力不够，且MVP阶段不需要）。

本计划产出一份可以直接执行的硬件选型清单、PCB模块排布方案、固件/算法代码分工方案。

## 二、PCB模块排布方案

### 2.1 设计原则
- 第一版PCB**只做互联载板**，不集成Pi本身（Pi Zero 2 W整板直接螺丝固定或魔术贴粘在镜架内侧，不拆解）
- 载板作用：把IR LED驱动电路、OLED供电/信号转接、USB/CSI线的理线固定点统一到一块小板上，减少散乱飞线
- 尺寸约束：镜腿内宽通常1.5-2cm，载板宽度控制在**15mm以内**，长度可以沿镜腿方向做长条形（40-60mm）

### 2.2 载板模块清单（从镜腿前端到后端排布）

```
镜腿前端(靠近镜框)                                    镜腿后端(靠近耳朵)
┌──────────┬──────────────┬─────────────┬──────────────┐
│ IR LED   │  OLED接口区   │  USB/CSI    │  电源输入接口  │
│ 驱动模块  │  (I2C 4pin)  │  理线固定点  │  (JST 2pin)  │
│          │              │             │              │
│ [限流电阻]│ [4pin排针]   │ [USB-A母座  │ [JST连接器]   │
│ [IR LED  │ (接OLED模块)  │  或直接走线  │ [5V->3.3V    │
│  本体,朝  │              │  到Pi的USB] │  降压(若需要)]│
│  内侧眼睛]│              │             │              │
└──────────┴──────────────┴─────────────┴──────────────┘
```

- **IR LED驱动区**：一个限流电阻（根据所选LED的正向电流计算，采购LED时务必要datasheet才能算）+ LED本体焊盘，朝向眼睛一侧镂空
- **OLED接口区**：4pin排针（VCC/GND/SDA/SCL），OLED模块本身不上这块板，用短排线连接，OLED物理位置贴着镜腿内壁靠近镜框一侧（方便光路反射到镜片上）
- **USB/CSI理线区**：不是真正的电路模块，是走线固定点（用小过线孔+热熔胶固定），因为USB线(接GC0308，原计划接OV9281，2026-10-30更新见上文摄像头选型变更)和CSI线(接场景摄像头)都是直接到Pi，不经过这块载板处理信号，载板只负责让线材不晃动
- **电源输入区**：JST 2pin接头接入来自腰间电池包的线，如果电池包出来的电压不是Pi需要的5V，这里放一个小型降压/稳压模块（多数18650+升压方案可以直接出5V，这种情况这里只是直通）

### 2.3 走线逻辑
- IR LED驱动 → 直接到Pi的一个GPIO（通过限流电阻，或用PWM调光则接一路MOSFET小电路）
- OLED → Pi的I2C总线（SDA=GPIO2, SCL=GPIO3，Pi Zero 2 W的40pin头上的标准I2C引脚）
- 电源 → 不经过Pi的GPIO，直接接Pi的5V/GND（通过Pi的USB口，或裸焊到PP5V0测试点，新手建议先用micro-USB口，走线更简单且可拆卸调试）

### 2.4 打样建议
第一版不追求柔性板，用**FR4硬板2层打样**（JLCPCB等，10片起订约几十元），验证模块布局和走线逻辑；镜腿弧度的贴合问题，第一版先用柔性排线桥接固定点+硬板分段的方式解决，不是一开始就上FPC（柔性PCB打样贵且设计容错低，不建议作为第一版）。

## 三、软件/固件分工（代码写在哪、怎么写）

### 3.1 目录结构（新建，与现有OV9281_test项目平行）

```
OV9281_test/
  glasses_system/              <- 新建目录，Pi Zero 2 W上运行的全部代码
    scene_capture.py           <- CSI场景摄像头采集（用picamera2库，Pi官方推荐）
    distractor_classifier.py   <- 闭集分类器（先用简单颜色/形状规则，MVP阶段不上深度学习）
    mask_renderer.py           <- 生成密集文字遮蔽图案，渲染到OLED
    fusion_main.py             <- 主循环：瞳孔坐标(复用pupil_detector_ellseg.py，2026-10-30前是pupil_detector.py，见摄像头选型变更) + 场景目标位置 → 投影坐标映射 → 驱动OLED
    oled_driver.py             <- SSD1306 I2C驱动封装（用luma.oled或Adafruit_SSD1306库）
```

- **复用不重写**：`fusion_main.py` 直接 `from pupil_detector_ellseg import detect_eye, detect_pupil`（接口和原来的`pupil_detector.py`一致，换一行import即可，见`261004/experiment_report.md`7h.2节）。原计划这里用的是`pupil_detector.py`（Haar cascade+Otsu阈值，轻量级传统算法），2026-10-30随摄像头选型一起更新为`pupil_detector_ellseg.py`（EllSeg深度学习模型）——**这个替换带来一个新的、原计划完全没有考虑过的风险，必须在往下推进前单独验证**：`pupil_detector.py`是纯OpenCV经典算法，在PC上能跑60-100+FPS，这正是原计划"Pi Zero 2 W算力够用"这个判断的前提；`pupil_detector_ellseg.py`依赖PyTorch跑一个真正的卷积神经网络，同样的PC（且是CPU推理，机器上有RTX 4070但没装CUDA版torch，见7f.2节）实测只有约6-8FPS（7f.6/7g.4/7i.10节多次验证的一致数字）。Pi Zero 2 W是四核Cortex-A53，没有AVX指令集、主频和缓存都远低于PC的x86 CPU，PyTorch在这种ARM板子上跑CNN推理大概率比PC上的6-8FPS还要慢得多——**这个数字现在完全是未知的，不能假设"PC上能跑，Pi上降级一点也能用"，必须实测**，对应3.2节第1步的风险标注
- **运行环境**：Pi Zero 2 W上装 Raspberry Pi OS Lite（无桌面，省资源）。~~通过SSH远程开发，用`D:\工业设计\python.exe`这台PC上的VSCode Remote-SSH插件连过去写代码~~ **2026-10-30更新：Pi Zero 2 W的WiFi一直连不上用户的网络，改为USB直连PC开发**（Pi Zero 2 W没有独立的以太网口，直连PC走的是USB OTG口的"gadget模式"，让Pi在USB线上模拟出一个网卡给PC用，再对这个虚拟网卡SSH，不是走WiFi）。这条只影响**开发阶段怎么连上去写代码**，不影响最终成品的架构——原计划里Pi的WiFi本来就只是给开发者远程连的，整机工作时的数据流全部是本地的（CSI摄像头直接进Pi、USB摄像头直接进Pi、I2C直接出OLED），没有任何一步依赖网络，所以即使Pi的WiFi一直不好用，也不卡最终"单根电源线"的佩戴形态。

### 3.2 开发顺序（避免一次性整合所有模块）

1. **先验证Pi能跑通现有算法——这一步现在隐藏着一个没有数据支撑的假设，必须先验证再往下走**：把`pupil_detector_ellseg.py`（连同它依赖的PyTorch运行时和EllSeg权重文件`weights/all.git_ok`，见`261004/experiment_report.md`7f.1节的获取方式）部署到Pi上，用GC0308通过USB接Pi，跑一遍`gc0308_rerun_ellseg_video.py`同一套逻辑的Pi移植版，确认检测率和PC上测的数字（静态图86.9%、固定安装后连续视频公平帧100%，见7i.6/7i.10节）量级一致——**这里的"量级一致"现在只能指成功率，不能指FPS**：FPS这边完全没有历史数字可参照（老计划里"15.17%/30.16%"那两个数字是`pupil_detector.py`时代的产物，连算法都换了，不再适用），Pi Zero 2 W能不能在可接受的帧率下跑动PyTorch+EllSeg，是一个全新的、没有先例的风险点，需要先实测这一个数字，再决定要不要在Pi Zero 2 W这个硬件档位上继续往下做——如果实测帧率低到不可用（比如个位数以下），本计划"随身算力单元用Pi Zero 2 W"这个最初的硬件选型判断本身可能需要重新评估，不是小修小补能解决的
2. **再单独验证CSI场景摄像头**：用`picamera2`库单独跑通拍照/取流，不接入任何检测逻辑
3. **再单独验证OLED显示**：用`luma.oled`库显示一行测试文字，确认I2C接线正确
4. **最后才做融合**：三个都单独验证通过后，再写`fusion_main.py`把它们串起来

### 3.3 密集文字遮蔽的具体实现思路
- `distractor_classifier.py`：对场景帧做预定义分类（MVP用简单方法，比如固定区域的亮度/色彩直方图匹配，或一个针对2-3个类别训练的极小MobileNet量化模型，视Pi Zero实测算力决定）
- 一旦判定某区域是"干扰物"，`mask_renderer.py`按该区域在场景帧里的像素坐标，结合已知的场景摄像头与潜望镜投影区域的几何映射关系（需要实际测量校准，类似本项目第十阶段计划做的5点标定逻辑，可以复用`calibration.py`里的仿射拟合方法），计算出在OLED上应该点亮文字的位置
- OLED driver用`luma.oled`的`ImageDraw`接口，循环绘制密集文字（如重复打印"///"或随机字符填充矩形区域）

## 四、验证方式

| 阶段 | 验证标准 |
|---|---|
| Pi跑通瞳孔检测 | 检测率与PC端数字量级一致（静态图86.9%、固定安装后连续视频公平帧100%附近，见7i.6/7i.10节），**FPS这项没有历史参照数字，必须先实测**（EllSeg在PC上CPU推理只有6-8FPS，Pi Zero 2 W算力明显更弱，这个数字完全未知——见3.2节风险标注，不能假设能用） |
| CSI场景摄像头 | 能稳定取流，记录实测FPS |
| OLED显示 | I2C通信成功，屏幕显示预期图案 |
| 几何映射校准 | 用类似calibration.py的5点标定方法，验证场景像素坐标→OLED投影坐标的映射误差在可接受范围内（需先定义"可接受"的量化标准） |
