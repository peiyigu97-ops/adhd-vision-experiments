## 一、本方案要回答的问题

在 261010 路线图（v2，**已废弃**）中，算力与显示全部压在 Raspberry Pi Zero 2 W 上，Pi 同时驱动两个摄像头、跑瞳孔检测、渲染 OLED 遮罩。本方案提出一个替代路径：

**抛弃树莓派 / 香橙派这类 Linux 小主板，直接用 PC 作为唯一的算力单元，ESP32-CAM 只作为"向外的场景相机 + OLED 驱动节点"，两者通过 WiFi 连接。**

提出的原始拓扑：

```
[GC0308 + IR]  ──USB──>  PC（瞳孔检测 + 解析用户注意力落点）
                          │
[ESP32-CAM]    ──WiFi──>  PC（场景图像上行）
                          │
                          └──WiFi──>  ESP32-CAM ──I2C──> OLED（光学遮挡输出）
```

数据流分两路：
- **眼动路**：GC0308（内置IR，见7b.1节）采集瞳孔图像 → PC用EllSeg解析 → 得到"用户在看向外部的哪个方向/哪个物体"
- **场景路**：ESP32-CAM 采集外部场景 → PC 判断该物体是否是干扰物
- **输出路**：判定为干扰物 → PC 回传 → ESP32-CAM 驱动 OLED → 光学遮挡

> **两个设备的连接方式不同，不要混：**
> - **ESP32-CAM**：独立供电（电池/电源，不经过 PC），与 PC 之间**全程无线**——只能是 WiFi（蓝牙带宽不够，见约束二），不需要任何线材连电脑。
> - **GC0308**：因为是 USB UVC 模块，必须有一根 **USB 线**直连 PC（见约束一），这是它的硬件形态决定的，无法绕开——这条约束是OV9281和GC0308共有的，换摄像头没有改变这一点。
>
> 下面"约束一"和"砍掉 Pi 的代价"说的都是 GC0308 这一根线，**不涉及 ESP32-CAM**。

**结论：方案成立，而且是本阶段务实的选择。但它有一个本质代价和两个硬约束，必须先接受再往下做。**

## 三、硬约束（不可绕过，需先接受）

### 约束一：GC0308 必须有一根 USB 线到 PC

`作品集/课程/261004/` 下已验证：GC0308 和 OV9281 一样是 **USB UVC 模块**（`gc0308/identify_gc0308.py` 枚举确认，近距离眼动模组，详见`261004/experiment_report.md`第7i节）。

UVC 流必须由 **USB Host** 接收。能当 Host 的设备就是 Linux 小主板——也就是本方案要抛弃的那一类。ESP32-S3 虽带 USB-OTG，但只有**全速 12Mbps**，720p 灰度单帧 0.92MB，换算下来 **不到 2fps**，等于不可用。

> **本方案的代价：砍掉 Pi = 佩戴者被一根 USB 线拴在电脑上。**
> USB 2.0 实际可靠长度 3~5m，再长需要主动延长线或带供电 HUB。

这条约束直接决定了方案的定位：

| 用途 | 是否可行 |
|---|---|
| 台面原型 / 课堂演示 | ✅ 完全可行，且是好选择 |
| 真的戴着走动 | ❌ 有线即不可穿戴 |

~~**如果最终目标是可穿戴，Pi 那条路必须保留，不能真的抛弃。**~~ **2026-10-30更新：Pi Zero 2 W的WiFi问题一直解决不了，用户已决定放弃这条路，接受"现阶段不是真·可穿戴"这个代价，专注把PC直控这条线跑通。**

### 约束二：只能走 WiFi，蓝牙直接否掉

这是必须先说清楚的——用户提出的"WiFi / 蓝牙连接方式"，蓝牙这一半不成立：

| 通道 | 实际吞吐 | 能否承载视频 |
|---|---|---|
| ESP32 BLE | 实际几 KB/s ~ 几十 KB/s（调优理论上限约 700kbps） | ❌ 差一个数量级 |
| BT Classic SPP | 约 100~200KB/s | ❌ 不够 |
| ESP32 WiFi TCP | 实际 5~15Mbps（相机并发时降到 3~8Mbps） | ✅ |

而且 **ESP32 的 WiFi 与蓝牙共享同一颗 2.4GHz 射频**，无法同时满速运行。

> **结论：WiFi 是唯一选项。蓝牙连当备用通道都不够。**

## 四、带宽与延迟的账

### 4.1 带宽

- VGA 640×480 JPEG（质量 12）≈ 30KB/帧
- 10fps → 300KB/s ≈ **2.4Mbps**（能塞进 ESP32 WiFi）
- ESP32-CAM 边拍边发的实际吞吐约 3~8Mbps

> **技术上限：VGA @ 10~15fps。** 想上 720p 或更高帧率，带宽立刻见底。

### 4.2 延迟链路（PC 全接管的朴素方案）

| 环节 | 耗时 |
|---|---|
| 场景采集 + JPEG 编码 | 15~30ms |
| WiFi 上行 | ~60ms |
| PC 解码 + 推理（GPU / CPU） | 20~50ms / 100~300ms |
| 结果回传 | ~10ms |
| OLED 刷新（400kHz I2C，全屏 1024B） | ~23ms |
| **合计** | **约 130~200ms（GPU 场景）** |

## 五、关键洞察：延迟对静止场景宽容，但转头会滑移

### 5.1 好消息：几何映射是固定的

场景相机、眼睛、OLED **刚性同装在一副眼镜上**，全部 head-locked。因此：

> **世界方向 → 场景相机像素 → OLED 像素** 是一个**固定映射**，靠一次标定即可确定。

261010 路线图第十阶段的 5 点标定逻辑（复用 `261004/calibration_ellseg.py` 的仿射拟合，2026-10-30更新：标定脚本已从`calibration.py`换成EllSeg版，见`261004/experiment_report.md`7h节）正好干这件事。

这意味着：**PC 慢一点，不影响"遮罩画在 OLED 的哪个位置"**——只影响"多快察觉到你在看干扰物"。

### 5.2 陷阱：遮罩与干扰物的运动不同步

遮罩画在 OLED 上，OLED 跟着头转：

- 头一转 → OLED 上的遮罩在**视网膜上不动**
- 而干扰物在**视网膜上动了** → 两者立刻错开

> **头转动时，每一帧的延迟都会变成遮罩滑移。**
> 头速 300°/s 时，200ms 延迟能滑 60°。

**这才是真正需要优化的目标，而不是带宽。**

| 场景 | 延迟容忍度 |
|---|---|
| 静止观看、静止干扰物 | 无所谓，几百 ms 都行 |
| 转头过程中 | 延迟 = 滑移，必须压到一帧级 |

## 六、推荐架构：把 FOMO 下放到 ESP32-CAM

`作品集/课程/260809/ADHD PlanA 技术方案整理.md` 中已记录：老师推荐的 **FOMO 在 ESP32 上约 100KB 内存**就能跑起来。这条线索在本方案中正好接上。

```
[GC0308 + IR] ──USB──> PC: 瞳孔检测(EllSeg) → 注视点坐标
                         │
                         └──WiFi（kbps 级）──> ESP32-CAM
                                                  │
                            FOMO 本地检测 + 本地绘制遮罩
                                                  ↓
                                               OLED
```

### 6.1 为什么这样更好

1. **遮罩定位不再等 PC 往返。** ESP32-CAM 自己知道干扰物在**自己画面**的哪个像素，而"自己画面像素 → OLED 像素"是固定标定矩阵。遮罩按相机帧率更新，延迟 ≈ 一帧 + OLED 刷新 ≈ **60~90ms**（对比朴素方案 200ms）。
2. **带宽从 Mbps 掉到 kbps。** PC 只发"注视点落在场景画面哪个像素"，几个字节 @30Hz。**场景视频根本不用传**。
3. **PC 的延迟变得无所谓。** PC 慢 200ms 只影响响应及时性，不影响遮罩画在哪。人盯手机是几百 ms 到几秒的事，可接受。
4. **与路线图第 5 条一致**：MVP 用闭集预定义分类（"手机屏幕""电视""广告牌"），不做开放式通用检测。

### 6.2 混合模式（如果要用 PC 的大模型）

保留 PC 算力，但分工明确、异步：

- **ESP32-CAM 跑 FOMO** → 负责"**快定位**"
- **PC 跑大模型** → 负责"**准判断**"

定位始终在本地，PC 的结论慢一点来也没关系。

## 七、具体工程坑

| # | 坑 | 说明与解法 |
|---|---|---|
| ① | **ESP32-CAM 无 IR-cut 滤光片** | AI-Thinker 版普遍不带（这也是它能夜视、白天偏粉的原因）。**GC0308的内置IR（见`261004/experiment_report.md`7b.1节）会直接打进场景相机**，导致偏色、对比度下降。同一副眼镜上串光几乎必然。解法：给场景相机加 IR-cut 滤光片，或两镜头间做物理遮光隔断。**2026-10-30更新：原文这里针对的是OV9281外挂的850nm补光灯，现在换成GC0308后，光源变成了模组自带的内置IR，串光风险本身没有消失，只是来源从"外挂灯"变成"模组自带"，解法不变** |
| ② | **别用"每帧一次 HTTP 请求"** | 10fps 下 TCP 握手 + HTTP 头开销太狠。用**长连接**（WebSocket 或裸 TCP + 二进制分帧） |
| ③ | **OLED 刷新与 WiFi 抢 CPU** | 双核分工：WiFi 协议栈钉 core 0，摄像头 + OLED 绘制钉 core 1 |
| ④ | **引脚冲突** | OLED 接 **GPIO14(SDA) / GPIO15(SCL)**，**避开 GPIO12**（MTDI strapping，上电电平不对会起不来）。GPIO16 已被 PSRAM 占用 |
| ⑤ | **供电反而简化** | 反正已被 USB 拴住，直接从 PC 引一路 5V——不用电池、不用担心 brownout。这是有线方案为数不多的实惠 |
